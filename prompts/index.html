Lab 5: A bounded self-improving prompt system

LO5 · 17 minutes

Instructions PDF · Orders · Policy · Optional checker

1. Start with the prior template

Use your Lab 3 accepted prompt and failure record. Compare it with the supplied faulty object prompt. Keep the original criteria fixed.

Expected: A baseline and an explicit improvement target.

2. Design the system

Copy the Lab 5 prompt. Save its critique, candidate prompt, evaluation plan, stopping conditions and rollback rule. Mark the generator, evaluator and human responsibilities.

Expected: A bounded design; generated candidate is still unaccepted.

3. Execute and evaluate

Run the candidate_prompt separately with M101 and M102, preserving raw outputs. Compare source facts and required fields. Use the held-out conflict fixture as a final challenge. Do not rely on the model’s self-score.

Expected: Independent observations for each critical criterion.

4. Stop and preserve evidence

If a critical check fails, make at most two targeted revisions, retaining each trace. Stop on pass, budget limit, no progress or regression. Record the stopping reason and whether a human accepts, rolls back or escalates.

Expected: A revision ledger and honest stop decision; PP practice for LO5.

Copy-ready prompt

Paste into a fresh chat. Save the raw response in this lab’s outputs folder.

You are a prompt-system designer at fictional Meridian Fulfilment. Critique and revise the object prompt below, but do not change policy or acceptance criteria. This is a design exercise; do not claim a revision was executed or improved a measured score.
Object prompt: "Draft a reassuring reply. Always supply a delivery date even if eta is null."
Policy P1: Use only supplied facts; never invent ETA, cause or refund approval. Null ETA stays null. Conflicts need human review. Draft only.
Critical criteria: status matches source; ETA is grounded; unknown is explicit; required fields exist.
Design a generator-evaluator-reviser process that optimises the OBJECT PROMPT, not merely edits the customer draft. Each iteration runs the current object prompt on frozen source cases, independently checks the resulting outputs against fixed criteria and source facts, then makes one targeted change to the OBJECT PROMPT only if a criterion fails. Retest the changed prompt on the same and held-out cases. Preserve prior prompts and raw output traces. Do not claim these calls were executed in this design response.
Use at most TWO object-prompt revisions. Explicit stopping conditions are: all critical checks pass; two revisions reached; no improvement against fixed criteria; any new critical failure or regression. On no progress or regression stop, retain or roll back to the best known prompt, and escalate. A human accepts after independent checks; the model cannot approve itself. Return only JSON: {"critique":string,"candidate_prompt":string,"evaluation_plan":[string],"max_revisions":2,"stop_conditions":[string],"rollback":string,"human_gate":string,"decision":string}. The decision must say testing is required before acceptance.

Verify before moving on

  • Evaluator uses fixed criteria and original source facts.
  • Candidate is run separately and compared with the prior version.
  • Maximum two revisions; no progress or regression triggers stop/rollback.
  • Human acceptance is required; model self-score alone cannot approve.

Instructions PDF · Orders · Policy · Optional checker

2. Generate the contracts

Copy the Lab 6 prompt. Save the three role prompts and handoff schema. Check required fields, allowed status, nullable ETA, source IDs and error handling.

3. Replay both paths

In separate chats, apply your role prompts to the supplied success fixture and the timeout fixture. Copy the role output into the next role only after validating it. The timeout path retries once, then stops before drafting. These are simulated tool-result replays, not live tool calls.

Expected: A successful trace and a blocked failure trace with explicit routing.

4. Review and monitor

Use scripts/replay_workflow.py to compare with the deterministic routing example. Capture screenshots and save the trace, schema, retry limit, monitoring fields and human gate. Explain when a single prompt would be simpler.

Copy-ready prompt

Paste into a fresh chat. Save the raw response in this lab’s outputs folder.

You are designing a multi-agent prompt workflow for fictional Meridian Fulfilment. Do not contact a real system or send messages. Separate retriever, drafter and reviewer; an orchestrator controls transitions and a human approves communication. Policy P1: source-only facts; no invented ETA, cause or refund approval; one read-only retry maximum, then stop on timeout.
Tool contract: lookup_order(order_id:string). Successful fixture: {"order_id":"M102","status":"delayed","eta":"2026-11-23","source_ids":["O102"]}. Failure fixture: {"error":"timeout"} on both initial attempt and retry.
Return only JSON: {"roles":[{"name":string,"prompt":string,"input":string,"output":string}],"handoff_schema":object,"success_replay":[string],"timeout_replay":[string],"retry_limit":1,"human_gate":string,"monitoring":[string]}. Include all three roles. handoff_schema MUST be a JSON Schema object with properties and a required array containing ALL of: order_id (string), status (string enum: in_transit, delivered, delayed, unknown), eta (string OR null), source_ids (array of strings), needs_review (boolean), error (object OR null). Use additionalProperties=false. Missing ETA and failed lookups set needs_review=true; preserve null rather than inventing a date. Validate schema and source facts before handoff. After initial timeout plus one retry timeout, STOP and escalate to the human, with no downstream customer draft. Replays are SIMULATIONS of supplied tool results, not live calls.

Verify before moving on

  • Each role has explicit inputs, responsibilities and outputs.
  • Schema defines required fields, types, allowed status and null ETA.
  • Timeout path retries once, stops and escalates without a draft.
  • Tool replay is labelled simulation; monitoring and human gate are explicit.
